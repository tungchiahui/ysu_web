# 人员资料 frontmatter 规范

生效日期：2026-10-20。学生和指导老师使用 `kind` 区分；一人一份 Markdown。学生按赛季记录组别和职务，没有顾问或梯队身份。

## 文件和地址

- 学生：`content/members/student/姓名.md`。
- 指导老师：`content/members/teacher/姓名.md`。
- 头像：`public/images/member_photo/姓名.jpg` 等。
- 详情页：`/team/姓名`，浏览器会对中文地址编码。姓名必须唯一，并与文件名一致。
- 同一人跨赛季只追加 `seasons`，不复制档案。目录不承担赛季语义。

## 字段约束

| 字段 | 学生 | 指导老师 | 类型与规则 |
| --- | --- | --- | --- |
| `kind` | 必填 `student` | 必填 `teacher` | 人员类别 |
| `name` | 必填 | 必填 | 非空字符串，文件名及详情页标识 |
| `affiliation` | 必填 | 必填 | 实际所属学院 |
| `image` | 可选 | 可选 | `/images/` 下存在的图片；省略时使用站点默认头像 |
| `grade` | 必填 | 不使用 | 2000-2099 范围内的四位整数，表示入学年份 |
| `seasons` | 至少一条 | 至少一条 | 赛季记录数组；支持多个赛季，每个年份只出现一次 |
| `department` | 不使用 | 可选 | 系、部门等非空字符串 |
| `titles` | 不使用 | 可选 | 非空字符串数组，表示职称、导师资格或校内职务 |
| `links` | 可选 | 可选 | 字符串键到公开 HTTP/HTTPS 链接的映射 |

## 赛季记录

每条记录的 `year` 必填，使用 2000-2099 的四位整数，不加引号。入学年份与赛季年份是独立字段。

学生每条记录还必须包含：

- `group`：机械组、电控组、硬件组、算法组、运营组，五选一。
- `roles`：队长、副队长、组长、项管、成员，至少一个，可兼任。

同一条记录中的职务不能重复。“成员”不与其他职务并列；队长、副队长互斥。`组长` 根据 `group` 显示为“机械组组长”等文字。担任队长、副队长、项管不会覆盖组别。

老师的赛季记录仅包含 `year`；不填写学生组别和职务。学生与老师均须填写赛季，不省略 `seasons` 或填写 `[]`。基础模板以 2027 为例，实际参与多个赛季时，在同一 `seasons` 列表中追加，不复制人员档案、不重复同一年；仅记录真实参与的年份，可以不连续。

学生每个赛季都需填写当年的 `group` 与 `roles`，不会继承上一年的值；换组、换职务写在新记录中，`grade` 始终保留实际入学年份。老师每个赛季只增加一条 `year`。具体示例见 [个人资料填写教程](../member-submission-kit/说明书.md#参加多个赛季怎么填)。不要将教学示例中的年份直接追加到实际资料。

## 网站展示

- 团队页面依次展示指导老师、团队负责人和各学生组别。队长、副队长、项管归入团队负责人，兼任组长也不在组内重复展示；其他组长排在各自组的成员前面。
- 分区与组长排序使用所选赛季的任职；全部赛季时使用最近一条符合组别、职务筛选的记录，避免不同年份的职务影响当前分区。
- 赛季、人员身份、组别、职务分别筛选。筛选按钮使用两位年份，例如 `27赛季`；frontmatter 和筛选值继续使用四位年份 `2027`。
- 卡片与详情的赛季值仅显示年份，不追加“赛季”二字。连续年份合并为 `2027–2029`，不连续时显示为 `2027–2028、2030`；当前真实成员仍只显示 `2027`。
- 学生与指导老师均不设置学校字段，页面和 frontmatter 中都不使用 `university`；学院字段 `affiliation` 保留。
- 选定赛季时，组别、职务和卡片信息使用同一赛季记录。
- 全部赛季下，组别和职务也必须在同一条记录中匹配，不能将不同年份的身份拼成一次任职。
- 全部赛季列表按最近一条任职记录归组；卡片和详情保留各赛季职务信息。选择某个组别时按该组展示符合记录的人。
- 指导老师独立展示，不属于五个学生组别。切换到指导老师身份时清除学生组别和职务筛选。
- 空组别不生成空白人员板块，五个组别的筛选选项始终保留。各组统一使用学生模板及相同的赛季、职务规则。

## 可选值和正文

不填写可选字段时直接省略，不使用 `null`、空字符串或“无”。`titles` 可使用空数组，`seasons` 不能为空。

`links` 是键名到 HTTP/HTTPS 网页地址的映射，不是固定平台枚举。完整的内置按钮名称映射为：`homepage` → 主页、`github` → GitHub、`gitcode` → GitCode、`blog` → 博客、`bilibili` → Bilibili、`google-scholar` → Google Scholar。键名按原样填写；其他键直接作为按钮文字，允许使用“抖音”“知乎”“作品集”等自定义名称。值必须为完整的 HTTP/HTTPS URL，不支持纯账号、邮箱、`mailto:`、`tel:` 或本地路径；同一键名不能重复。完整写法和常见平台示例见 [个人资料填写教程](../member-submission-kit/说明书.md#第三步填写个人链接和介绍可选)。

不接受已删除的学校字段 `university`、旧字段 `type`、`role`、`time`、`advisor`，或额外的梯队字段。新增字段须先更新规范及校验规则。两行 `---` 后的 Markdown 正文可自由填写个人介绍、研究方向、项目和历史经历。


### GitCode 与任务看板对应

需要让研发看板显示本人的队员姓名、头像和个人介绍入口时，在这份资料的 `links` 下填写 `gitcode` 个人主页，例如 `https://gitcode.com/example-member`。这是已有的链接字段，不新增顶层字段，也不需要另填 EO 人员表。填写完整 HTTPS 个人主页，不使用仓库地址、查询参数、组织项目列表或占位名称。

看板优先按接口提供的公开账号对应；贡献者接口只有 Git 作者名时，仅与已填写的 GitCode 账号精确匹配（账号不区分大小写），作者别名与账号不同则不会凭姓名猜测。匹配后使用这份档案的姓名、头像和站内介绍链接；未匹配保留 GitCode 名称，头像显示圆形燕鹰队徽，进入已知 GitCode 个人主页或相关仓库。缺少成员头像或图片加载失败也回退队徽。

一个 GitCode 账号应只对应一份成员档案；重复填写时看板不擅自选择。资料对应只改变展示，不会将不同邮箱的同名 Git 作者自动合并成一个身份。内容仓库 main 推送后由 EO 重新生成，新增或修改链接随部署生效。

## 校验与发布

网站仓库的 `utils/member-schema.mjs` 是字段与枚举定义；`scripts/member-check.mjs` 在内容同步后检查原始 YAML、未知字段、条件必填、年份和职务冲突、重复姓名、文件名及头像存在性。`predev`、`prebuild`、`pregenerate` 自动执行检查，也可单独运行 `npm run members:check`。网站仓库的 `npm run members:test` 覆盖字段与跨赛季筛选回归检查。

网站和内容分仓维护。内容仓库 `main` 推送通过部署钩子触发 EO，网站仓库 `main` 推送通过 EO Git 集成触发；构建发布均由 EO 完成。GitHub Build 仅做额外检查，不是发布前置条件。

## 填写说明

填写说明使用 `member-submission-kit/说明书.md`，不再提供 PDF。模板与示例位于同一目录，不会进入公开成员列表。
